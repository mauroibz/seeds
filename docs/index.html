Seeds is a lightweight operating method for projects carried by agents across many sessions — one pass, one milestone:

  • Understand — context from the repository, not chat history
  • Decide — hard-to-reverse choices go to the owner; the rest proceed, recorded
  • Slice — one bounded milestone, executable acceptance criteria
  • Build — that milestone and nothing else, in verifiable increments
  • Verify — proved where it can actually fail: the app, the data, never a mock
  • Hand off — evidence plus a rewritten handoff; the next session starts from reality

Small loop, high leverage: nothing lives only in chat history, green means it actually works, and any agent, any session, picks up where the last one stopped.

What it establishes

Agents write code fast. What breaks projects is everything around the code: requirements that lived in chat history, a green suite that never opened the app, decisions nobody wrote down, and a session that died before the next one knew where to start.

Explicit sources of truthNo fact lives only in chat history. Authority is assigned by concern — the plan owns scope, migrations own schema, the handoff owns resume state.
One active milestoneBounded outcome, verifiable criteria, explicit non-scope. Small user-directed fixes take a light path instead of milestone ceremony.
Proof, not plausibilityA mock of the thing being proved is not proof. User-visible work requires a real walkthrough against realistic data — because a product once shipped broken behind 122 passing tests.
Durable historyAppend-only decisions and worklog; a rewritten handoff that states current reality and the exact next action for whoever — whatever — picks up next.

The incident behind the gate

After thirteen milestones, one Seeds-run application had 122 passing backend tests, 38 passing frontend tests, 86% coverage — and failed its basic purpose. No required check had ever run the application and watched the flow.
